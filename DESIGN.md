# Test Station Design Notes

## System boundary / protocol

The preflashed Teensy exposes a USB virtual serial port and streams eight comma-separated floating-point values per line, often with a trailing comma. Commands are raw ASCII `baseline` or `response:XX` (XX = 1..25 Hz) **without a newline**, as verified using `pyserial` on COM6. The worker treats single-number lines as optional frequency acknowledgements and detects the device's explicit frequency rejection. During testing this device rejected 20–25 Hz even though the exercise allows those values. The app does not flash firmware. The GUI indicates commands *sent*, not an independently confirmed physical actuator state.

## Architecture and threading

`main.py` owns the Qt GUI, plotting buffers, test sequence, result table, and output files. A `QThread` runs serial reads/writes and emits `(host_receive_timestamp, eight_values)` samples using `time.perf_counter()`. The GUI and reader use that same monotonic clock for deadlines and samples. GUI-to-worker commands go through a thread-safe queue: the GUI never directly writes a live `Serial` object from another thread. Plots redraw every 50 ms, while serial samples stream independently, avoiding a GUI refresh bottleneck. Each chart shows a rolling five-second window. A 20 ms Qt timer drives the state machine; it does not control the sampling rate. The app records when the worker *actually writes* each command, then starts settle/capture intervals.

## Test state machine

`IDLE → WAIT_BASELINE_COMMAND → BASELINE_SETTLE → BASELINE_CAPTURE → (WAIT_RESPONSE_COMMAND → EXCITE_SETTLE → EXCITE_CAPTURE → EVALUATING) × N → PASS/FAIL`. Explicitly rejected frequencies enter `WAIT_REJECTED`, request baseline, and are recorded before the sequence continues. The final result is `ERROR` if any were rejected. In batch mode the sequence repeats with a new baseline for each run; completed results are compared and saved incrementally. Serial errors, invalid timing, malformed or insufficient data, or command write timeouts stop the batch with `ERROR`; operator cancellation leads to `ABORTED`. The app requests `baseline` on normal completion, error, and abort if connected. The waveform buffers for baseline and each excitation are separate, and samples outside each capture window are excluded. Controls that could change parameters mid-test are disabled. The per-frequency results remain visible after the run.

## Signal model and AC coupling

Individual channels have different DC offsets and noise. The baseline noise estimate is `std(x_baseline)` (sample standard deviation, after mean subtraction). In the excited window, the software fits `x(t) = a·sin(2πft) + b·cos(2πft) + c` by least squares. The intercept `c` removes DC mathematically, without requiring a hardware AC-coupling capacitor. Peak response amplitude is `sqrt(a²+b²)`. The single-frequency fit rejects other frequencies better than raw peak-to-peak or total RMS, important for channels with independent noise or large DC offsets.

SNR is `20 log10[(amplitude/√2)/baseline_RMS_noise]`. Each channel passes only if amplitude and SNR meet their minimums and any enabled maximum baseline noise, maximum response amplitude, and raw signal boundaries are satisfied. Common defaults can be overridden per channel and frequency. Optional limits are disabled by default because no specifications were supplied. Default minimum amplitude 100 and minimum SNR 15 dB are exploratory settings, not calibrated product specifications. The user can change common thresholds in the GUI and all limits in settings.json. Test frequency defaults to 10 Hz; frequency selection spans 1–25 Hz, though the tested device rejected 20–25 Hz.

## Timing, failure modes, and limitations

The assignment describes 100 Hz samples, but captured host receive rates were approximately 150 rows/s. Therefore the fitted phase uses per-sample **host monotonic arrival times** rather than `sample_index/100`. The displayed effective receive rate helps identify discrepancies. This is not true hardware timestamping: packet buffering and OS scheduling can cause timing jitter and degrade sine fitting. More accurate production evaluation would require device timestamps or hardware sampling metadata and a calibrated excitation source. The application treats malformed or incomplete captures and a lost connection as test errors, not failing sensors. Optional configured signal bounds can flag samples at or beyond those limits but cannot establish physical clipping; harmonics, phase, actuator feedback, and calibrated product limits are not measured. A reported frequency acknowledgement does not verify the physical actuator state.

## Traceability, outputs, verification and AI use

Each completed run saves CSV baseline and excited samples with relative host timestamps and a JSON summary including timestamps, test port/frequency, thresholds, capture durations, received sample rates, and per-channel metrics/results. Tests cover protocol, synthetic signal analysis, GUI startup, sequencing, log files, abort, and insufficient data. A full 1–25 Hz sequence and an abort were exercised through the GUI event loop with the physical Teensy; the device rejected 20–25 Hz. Visual review, unexpected disconnects, and other operating systems remain to be checked. See [REPORT.md](REPORT.md) for measured results. AI was used to draft the Python code, test structure, and documentation; decisions around thresholds and potential sensor defects must be validated experimentally rather than treated as ground truth.
