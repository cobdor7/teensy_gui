# Test Station Design Notes

## System boundary / protocol

The preflashed Teensy exposes a USB virtual serial port and streams eight comma-separated floating-point values per line, often with a trailing comma. Commands are raw ASCII `baseline` or `response:XX` (XX = 1..25 Hz) **without a newline**, as verified using `pyserial` on COM6. The worker treats single-number lines as optional frequency acknowledgements and detects the device's explicit frequency rejection. During testing this device rejected 20–25 Hz even though the exercise allows those values. The app does not flash firmware. The GUI indicates commands *sent*, not an independently confirmed physical actuator state.

## Architecture and threading

`main.py` owns the Qt GUI, plotting buffers, test sequence, result table, and output files. A `QThread` runs serial reads/writes and emits `(host_receive_timestamp, eight_values)` samples using `time.perf_counter()`. The GUI and reader use that same monotonic clock for deadlines and samples. GUI-to-worker commands go through a thread-safe queue: the GUI never directly writes a live `Serial` object from another thread. Plots redraw every 50 ms while serial reads run in the worker, although a busy GUI can delay processing queued samples. Each chart shows a rolling five-second window. A 20 ms Qt timer drives the state machine; it does not control the sampling rate. The app records when the worker *actually writes* each command, then starts settle/capture intervals.

At the end of a capture, the GUI asks the worker for a marker and waits for it before checking the sample count. The marker follows the worker's earlier sample signals, allowing samples already read during the capture to reach the GUI even if rendering delayed their delivery. Sample timestamps still define the original capture window, and missing data and excessive gaps remain errors.

## Test state machine

`IDLE → WAIT_BASELINE_COMMAND → BASELINE_SETTLE → BASELINE_CAPTURE → (WAIT_RESPONSE_COMMAND → EXCITE_SETTLE → EXCITE_CAPTURE → EVALUATING) × N → PASS/FAIL`. Explicitly rejected frequencies enter `WAIT_REJECTED`, request baseline, and are recorded before the sequence continues. The final result is `ERROR` if any were rejected. In batch mode the sequence repeats with a new baseline for each run; completed results are compared and saved incrementally. Serial errors, invalid timing, malformed or insufficient data, or command write timeouts stop the batch with `ERROR`; operator cancellation leads to `ABORTED`. The app requests `baseline` on normal completion, error, and abort if connected. The waveform buffers for baseline and each excitation are separate, and samples outside each capture window are excluded. Controls that could change parameters mid-test are disabled. The per-frequency results remain visible after the run.

## Signal model and AC coupling

Individual channels have different DC offsets and noise. The baseline noise estimate is `std(x_baseline)` (sample standard deviation, after mean subtraction). In the excited window, the software fits `x(t) = a·sin(2πft) + b·cos(2πft) + c` by least squares. The intercept `c` removes DC mathematically, without requiring a hardware AC-coupling capacitor. Peak response amplitude is `sqrt(a²+b²)`. The single-frequency fit rejects other frequencies better than raw peak-to-peak or total RMS, important for channels with independent noise or large DC offsets.

SNR is `20 log10[(amplitude/√2)/baseline_RMS_noise]`. Each channel passes only if amplitude and SNR meet their minimums and any enabled maximum baseline noise, maximum response amplitude, and raw signal boundaries are satisfied. Common defaults can be overridden per channel and frequency. Optional limits are disabled by default because no specifications were supplied. The default minimum amplitude of 100 and minimum SNR of 15 dB were exploratory choices in the initial implementation; their specific values were not documented as derived from calibrated product specifications or a known-good population. The user can change common thresholds in the GUI and all limits in settings.json. Test frequency defaults to 10 Hz; frequency selection spans 1–25 Hz, though the tested device rejected 20–25 Hz.

## Timing, failure modes, and limitations

The assignment describes 100 Hz samples, but captured host receive rates were approximately 150 rows/s. Therefore the fitted phase uses per-sample **host monotonic arrival times** rather than `sample_index/100`. The displayed effective receive rate helps identify discrepancies. This is not true hardware timestamping: packet buffering and OS scheduling can cause timing jitter and degrade sine fitting. More accurate production evaluation would require device timestamps or hardware sampling metadata and a calibrated excitation source. The application treats malformed or incomplete captures and a lost connection as test errors, not failing sensors. Optional configured signal bounds can flag samples at or beyond those limits but cannot establish physical clipping. The automatic evaluation does not measure harmonics, phase, or actuator feedback; offline analysis found a strong second harmonic on sensor 8, as described in the report. A frequency acknowledgement does not verify the physical actuator state.

## Traceability, outputs and verification

Each completed run saves CSV baseline and excited samples with relative host timestamps and a JSON summary including timestamps, test port/frequency, thresholds, capture durations, received sample rates, and per-channel metrics/results. Tests cover protocol, synthetic signal analysis, GUI startup, sequencing, log files, abort, and insufficient data. A full 1–25 Hz sequence and an abort were exercised through the GUI event loop with the physical Teensy; the device rejected 20–25 Hz. Visual review, unexpected disconnects, and other operating systems remain to be checked. See [REPORT.md](REPORT.md) for measured results.

## AI usage and review

AI was used to draft Python code, the test structure, and documentation. In the later work documented here, OpenAI Codex inspected the project, added an extra configurable settling interval before the first excited capture in each run, added GUI controls for the common raw-signal limits, and addressed delayed sample delivery during capture. Codex also updated the configuration, documentation, and automated tests, ran the test suite, and exercised the application with a connected Teensy. The latest suite passed 47 tests using the local Python environment; its serial and GUI tests use simulated inputs and an offscreen display.

On November 16, 2026, source-app runs on COM5 evaluated 1–19 Hz at roughly 150 host-received samples per second; the device rejected 20–25 Hz. A two-run 10 Hz batch confirmed one second of settling for each run's first excitation, and temporary GUI limits of −100 to 100 triggered range failures without being saved. A direct serial capture compared two-second fits immediately after the command and two seconds later at 1 and 10 Hz; response amplitudes were broadly similar in that single trial. This comparison does not establish physical onset time or prove the settling delay is sufficient. Following a report of insufficient samples, two additional source-app hardware runs completed, including one with a deliberately stalled GUI; the exact reported shortfall was not reproduced. Evidence is in the local, Git-ignored `runs/` directory, including the full sweep `test_20261117T034108_557374Z`. The Windows executable in `dist/` passed an offscreen startup smoke test after the sample-delivery change; that executable has not been checked with the Teensy.

Given the time constraints, the following need further review:

- **Physical timing:** The additional default 0.5-second first-excitation delay was chosen as a small initial allowance, not derived from actuator response measurements. The checks above confirm the sequence and provide one waveform comparison, but do not establish physical onset or settling; repeat measurements over devices and frequencies with independent actuator timing.
- **Acceptance criteria:** The amplitude and SNR defaults are exploratory. Obtain calibrated limits and review the signal model, the SNR calculation, channel/frequency overrides, and boundary behavior against the actual device and product requirements. A flagged range boundary does not prove clipping or a sensor defect.
- **Sampling and protocol:** Host arrival timestamps can be distorted by buffering, and a sent command or optional acknowledgement does not confirm actuator state. Investigate the reported 20–25 Hz rejections, possible missing samples, disconnects, and timing jitter with real hardware.
- **Deployment and usability:** Review the visible GUI and error handling on the target system and validate the packaged executable on the target hardware. The hardware checks above used the source app, not the packaged app.
